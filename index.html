The one score that is not about the model

Responses that ran to the generation ceiling and were cut off mid-object, measured on the lora run: dev 6 of 8, qe 1 of 16. The counter was added after the earlier evals, so it is reported once, but the cause is the shape of the training targets, so it applies to every arm.

This is why dev scores low in every arm. Its targets emit the changes array first (whole file bodies, 8,294 tokens at the 90th percentile) and the four other required fields (commit_message, pr_title, pr_body, summary) come after it. Exhaust the budget inside changes and all four are missing at once, which reads as a schema failure rather than a truncated response.

The fix is a key reorder in the training targets, not more training: put the cheap required scalars before the expensive array, so a cut-off answer still carries them. Not applied here, it needs a retrain, and changing the data would have invalidated the LoRA comparison below.

The scorer

Deterministic and offline. No judge model, no API call, no sampling, so the same response always earns the same score and anyone can re-run it. Four components, weighted:

weightwhat it checks
0.30schema: every required field present, correct type, arrays meet their minimum length
0.20enums: values drawn from the platform's real enum sets, not invented ones
0.35rigor: concrete file paths, executable reproduction steps, a rollback that is a procedure rather than 'revert the commit'
0.15clean: no TODO, no <insert name>, no lorem ipsum, no placeholder scaffolding

The same scorer rates the platform's own production output 0.999. That is the check that matters: if it could not rate known-good work near 1.0, the scorer would be the broken thing, not the model.

"""
Deterministic scorer for the QDev crew adapter.

No judge model, no API calls, no randomness — the same philosophy as the
platform's governance eval harness. Run it on a laptop, run it in CI, run it
a thousand times and get the same number.

Design note on fairness: `extract_json` is deliberately GENEROUS. A base model
that wraps valid JSON in prose or a markdown fence still gets full credit for
emitting it. Being strict there would inflate the before/after gap by
punishing formatting the tokenizer never saw, which would make the whole
comparison dishonest.
"""
from __future__ import annotations

import json
import re

from .schemas import SPECS, FILLER_PATTERNS, FILLER_EXACT, PRIORITY

FENCE = re.compile(r"```(?:json|JSON)?\s*(.*?)```", re.S)
_FILLER_RE = [re.compile(p, re.I) for p in FILLER_PATTERNS]


# ══════════════════════════ extraction ═══════════════════════════════════
def extract_json(text: str) -> tuple[dict | None, str]:
    """Pull the most plausible JSON object out of a raw completion.

    Returns (obj, how) where `how` records which strategy succeeded, so the
    report can show *how* the base model was failing, not just that it did.
    """
    if not text or not text.strip():
        return None, "empty"
    t = text.strip()

    # 1. the whole thing is JSON
    try:
        o = json.loads(t)
        return (o, "clean") if isinstance(o, dict) else (None, "not-object")
    except Exception:
        pass

    # 2. inside a markdown fence
    for m in FENCE.findall(t):
        try:
            o = json.loads(m.strip())
            if isinstance(o, dict):
                return o, "fenced"
        except Exception:
            continue

    # 3. brace matching — longest balanced object anywhere in the text
    best = None
    for start in (i for i, ch in enumerate(t) if ch == "{"):
        depth, in_str, esc = 0, False, False
        for i in range(start, len(t)):
            ch = t[i]
            if in_str:
                if esc:
                    esc = False
                elif ch == "\\":
                    esc = True
                elif ch == '"':
                    in_str = False
                continue
            if ch == '"':
                in_str = True
            elif ch == "{":
                depth += 1
            elif ch == "}":
                depth -= 1
                if depth == 0:
                    frag = t[start:i + 1]
                    if best is None or len(frag) > len(best):
                        best = frag
                    break
        if best and len(best) > len(t) * 0.6:
            break
    if best:
        try:
            o = json.loads(best)
            if isinstance(o, dict):
                return o, "embedded"
        except Exception:
            pass

    # 4. a tool_use envelope
    for key in ("input", "arguments", "parameters", "tool_input"):
        m = re.search(rf'"{key}"\s*:\s*(\{{)', t)
        if m:
            sub, _ = extract_json(t[m.start(1):])
            if sub:
                return sub, "tool-envelope"
    return None, "unparseable"


# ══════════════════════════ generic checks ═══════════════════════════════
def _ratio(ok: int, total: int) -> float:
    return 1.0 if total == 0 else ok / total


def check_schema(obj: dict, spec: dict) -> tuple[float, list]:
    notes, ok, total = [], 0, 0
    arrays = spec.get("arrays", {})
    for k in spec["required"]:
        total += 1
        v = obj.get(k)
        # An empty array is only a failure when the array rule demands members.
        # `review.findings` has min=0 because a clean APPROVE genuinely has no
        # findings — counting that as missing would score correct output as
        # broken, and (worse) teach the adapter to always invent a finding.
        allow_empty = isinstance(v, list) and arrays.get(k, {}).get("min", 1) == 0
        if v is None or (isinstance(v, (str, list, dict))
                         and len(v) == 0 and not allow_empty):
            notes.append(f"missing/empty:{k}")
        else:
            ok += 1
    for k, want in spec["types"].items():
        if k in obj and obj[k] is not None:
            total += 1
            if isinstance(obj[k], want):
                ok += 1
            else:
                notes.append(f"wrongtype:{k}={type(obj[k]).__name__}")
    for k, rule in spec.get("arrays", {}).items():
        v = obj.get(k)
        if isinstance(v, list):
            total += 1
            if len(v) >= rule["min"] and all(isinstance(x, rule["of"]) for x in v):
                ok += 1
            else:
                notes.append(f"array:{k} n={len(v)} min={rule['min']}")
    for arr, keys in spec.get("item_required", {}).items():
        for i, item in enumerate(obj.get(arr, []) or []):
            if not isinstance(item, dict):
                notes.append(f"item:{arr}[{i}] not-object")
                total += 1
                continue
            for k in keys:
                total += 1
                if item.get(k):
                    ok += 1
                else:
                    notes.append(f"item:{arr}[{i}].{k}")
    return _ratio(ok, total), notes


def check_enums(obj: dict, spec: dict) -> tuple[float, list]:
    notes, ok, total = [], 0, 0
    for k, allowed in spec.get("enums", {}).items():
        if k in obj:
            total += 1
            if obj[k] in allowed:
                ok += 1
            else:
                notes.append(f"enum:{k}={obj[k]!r}")
    for arr, rules in spec.get("item_enums", {}).items():
        for i, item in enumerate(obj.get(arr, []) or []):
            if not isinstance(item, dict):
                continue
            for k, allowed in rules.items():
                if k in item:
                    total += 1
                    if item[k] in allowed:
                        ok += 1
                    else:
                        notes.append(f"enum:{arr}[{i}].{k}={item[k]!r}")
    return _ratio(ok, total), notes


def _walk_strings(o):
    if isinstance(o, str):
        yield o
    elif isinstance(o, list):
        for v in o:
            yield from _walk_strings(v)
    elif isinstance(o, dict):
        for v in o.values():
            yield from _walk_strings(v)


def check_clean(obj: dict) -> tuple[float, list]:
    """Penalise placeholder text — the classic way a weak model looks
    schema-correct while being useless.

    Deliberately conservative: matches whole words and template markers only.
    'fill in all fields' and 'input placeholder text' are real QA phrases and
    must NOT be flagged.
    """
    hits: list[str] = []
    for s in _walk_strings(obj):
        low = s.strip().lower()
        if low in FILLER_EXACT:
            hits.append(f"empty-field:{low}")
            continue
        for pat in _FILLER_RE:
            m = pat.search(low)
            if m:
                hits.append(f"filler:{m.group(0)[:24]}")
                break
    uniq = list(dict.fromkeys(hits))
    return max(0.0, 1.0 - 0.25 * len(uniq)), uniq[:4]


# ══════════════════════════ per-task rigor ═══════════════════════════════
def rigor_plan(o: dict) -> tuple[float, list]:
    n, notes = [], []
    ac = o.get("acceptance_criteria") or []
    n.append(1.0 if len(ac) >= 3 else len(ac) / 3)
    good = sum(1 for a in ac if isinstance(a, str) and len(a) >= 20)
    n.append(_ratio(good, len(ac)))
    if len(ac) < 3:
        notes.append(f"thin-ac:{len(ac)}")
    n.append(1.0 if 0 < len(str(o.get("title", ""))) <= 120 else 0.0)
    n.append(1.0 if len(str(o.get("description_md", ""))) >= 100 else 0.0)
    return sum(n) / len(n), notes


def rigor_dev(o: dict) -> tuple[float, list]:
    ch = [c for c in (o.get("changes") or []) if isinstance(c, dict)]
    if not ch:
        return 0.0, ["no-changes"]
    n, notes = [], []
    rel = sum(1 for c in ch if isinstance(c.get("path"), str)
              and not c["path"].startswith("/") and "\\" not in c["path"])
    n.append(_ratio(rel, len(ch)))
    if rel < len(ch):
        notes.append("bad-paths")
    paths = [c.get("path") for c in ch]
    n.append(1.0 if len(set(paths)) == len(paths) else 0.5)
    body = str(o.get("pr_body", ""))
    n.append(1.0 if ("##" in body and len(body) > 80) else 0.0)
    cm = str(o.get("commit_message", ""))
    n.append(1.0 if re.match(r"^(feat|fix|chore|refactor|docs|test|perf)(\(.+\))?: .+", cm) else 0.0)
    if not re.match(r"^(feat|fix|chore|refactor|docs|test|perf)", cm):
        notes.append("non-conventional-commit")
    return sum(n) / len(n), notes

STEP 1.  The idea

   Fine-tuning learns an update dW and adds it:

        W' = W + dW

   dW is the same size as W, so training it costs
   as much as the whole model.

   LoRA splits dW into two thin matrices:

        dW = A x B

        A has size  (d_in  x  r)
        B has size  (r  x  d_out)

   So instead of training  d_in x d_out  numbers,
   I train  r x (d_in + d_out)  numbers.


STEP 2.  My model's numbers

        hidden size  d  = 4096
        layers       L  = 32
        MLP inner    f  = 14336
        attention heads = 32
        kv heads        = 8
        rank         r  = 16

   There are only 8 kv heads, not 32.

        head dim  = 4096 / 32 = 128

                  = 8 x 128
                  = 1024

   So k_proj and v_proj go from 4096 to 1024.
   Not 4096 to 4096.

         15.0 / 4.2 = 3.6 times smaller than LoRA


STEP 5.  Why NF4 and not ordinary int4?

   4 bits gives 2 x 2 x 2 x 2 = 16 slots.
   The only question is where to put those 16 slots.

   Ordinary int4:
        Spread them evenly.
        scale = absmax / 7, codes -7 to +7
        gap between levels = 1/7 = 0.1429, the same everywhere.

   NF4:
        Put them at the quantiles of a normal curve, so each
        slot covers the same amount of probability:

             1 / 16 = 0.0625 = 6.25 % of the weights per slot

        This makes the gaps uneven on purpose:
             near zero      the gap is about 0.080
             near the edges the gap is about 0.304

   Model weights are shaped like a normal curve, so most of
   them sit near zero. NF4 puts the fine detail where the
   weights actually are.

        I measured this on 131,072 samples:
        NF4 error is 14.6 % lower than int4.


STEP 6.  Double quantization - squeeze the scales too

   Every block of 64 weights needs its own scale, stored
   as fp32 (32 bits). That is extra cost on top of the 4 bits:

        32 bits / 64 weights = 0.500 bits per weight

   Now store those scales as int8 instead, and add one
   fp32 scale for each 256 of them:

        8 bits / 64            = 0.125
        32 bits / (64 x 256)   = 0.002
                                 -----
                                 0.127 bits per weight

        Saved = 0.500 - 0.127 = 0.373 bits per weight

   Across the whole model:

        7,248,000,000 x 0.373 = 2,703,504,000 bits
        2,703,504,000 / 8     =   337,938,000 bytes
                              =          0.34 GB

   So a "4-bit" weight really costs 4 + 0.127 = 4.127 bits.

==============================================================================
  1.  Why quantize at all
==============================================================================

  A parameter is just a number, and you choose how many bits to spend on it.
  7,248,000,000 parameters, priced per precision:

  precision    bits  bytes/param   model size   vs fp32
  -----------------------------------------------------
  float32        32         4.00       29.0 GB        1x
  float16        16         2.00       14.5 GB        2x
  int8            8         1.00        7.2 GB        4x
  nf4             4         0.50        3.6 GB        8x

  That is the entire motivation. Same weights, fewer bits each, and the model
  goes from "needs a data centre" to "fits on a rented GPU".


==============================================================================
  2.  int8 quantization, worked by hand
==============================================================================

  Map a real range onto an integer grid.

      scale       s = (x_max - x_min) / (q_max - q_min)
      zero point  z = the real value that lands on integer 0
      quantize    q = round((x - z) / s)
      dequantize  x_hat = s*q + z

  For x in [-1, 1] onto int8 codes -127 .. 128:

      s = (1 - (-1)) / (128 - (-127))
        = 2 / 255
        = 0.00784314

      z = -0.003922          (symmetric: zero maps to zero)

           x    q = round((x-z)/s)    x_hat = s*q + z   abs error
  ---------------------------------------------------------------
      0.7500                    96           0.749020    0.000980
      0.1234                    16           0.121569    0.001831
     -0.5000                   -63          -0.498039    0.001961
      0.0039                     1           0.003922    0.000022
     -0.9999                  -127          -1.000000    0.000100

  The error is bounded by half a step: s/2 = 0.003922.
  That is the guarantee. Nothing you quantize into this grid can be off by
  more than 0.003922, and on average it is about half that again.


==============================================================================
  3.  Blockwise quantization, on eight real weights
==============================================================================

  One scale for a whole 7B tensor would be dominated by its single largest
  value. So quantization is done per BLOCK, with its own absmax:

      absmax = max(|w|) over the block
      each weight is normalised to w / absmax, in [-1, 1]
      then snapped to the nearest level of a 16-entry code book

  Our eight weights:

      +0.0031
      -0.0142
      +0.0087
      -0.0009
      +0.0410
      -0.0056
      +0.0021
      -0.0198

      absmax = 0.0410

  Normalised (w / absmax), which is what actually gets quantized:

      +0.0031 / 0.0410 = +0.0756
      -0.0142 / 0.0410 = -0.3463
      +0.0087 / 0.0410 = +0.2122
      -0.0009 / 0.0410 = -0.0220
      +0.0410 / 0.0410 = +1.0000
      -0.0056 / 0.0410 = -0.1366
      +0.0021 / 0.0410 = +0.0512
      -0.0198 / 0.0410 = -0.4829

==============================================================================
  4.  NF4 vs int4 on those same eight weights
==============================================================================

  Four bits gives 16 slots. The only question is where to put them.

  int4, absmax scaling: evenly spaced, scale = absmax/7, codes -7 .. +7

      -1.000  -0.857  -0.714  -0.571  -0.429  -0.286  -0.143  +0.000
      +0.143  +0.286  +0.429  +0.571  +0.714  +0.857  +1.000

  NF4: 16 levels at the equal-probability quantiles of a normal

      -1.000  -0.696  -0.525  -0.395  -0.284  -0.185  -0.091  +0.000
      +0.080  +0.161  +0.246  +0.338  +0.441  +0.563  +0.723  +1.000

  Notice NF4's levels bunch up near zero and thin out at the tails. That is
  the whole idea: each level carries 6.25% of the
  probability mass (1/16), so resolution follows where the weights actually
  are instead of being spread evenly over a range they mostly do not occupy.

  Snapping our block with each code book:

           w    int4 recon      |err|     NF4 recon      |err|
  ------------------------------------------------------------
     +0.0031      +0.00586    0.00276      +0.00326    0.00016
     -0.0142      -0.01171    0.00249      -0.01619    0.00199
     +0.0087      +0.00586    0.00284      +0.01009    0.00139
     -0.0009      +0.00000    0.00090      +0.00000    0.00090
     +0.0410      +0.04100    0.00000      +0.04100    0.00000
     -0.0056      -0.00586    0.00026      -0.00373    0.00187
     +0.0021      +0.00000    0.00210      +0.00326    0.00116
     -0.0198      -0.01757    0.00223      -0.02153    0.00173

      int4  mean abs error = 0.001696    rmse = 0.002004
      NF4   mean abs error = 0.001150    rmse = 0.001349

  On eight weights this is anecdote, not evidence. Measured properly over
  131,072 samples in blocks of 64, NF4's mean squared error is 14.6 % lower
  than int4's, and the margin held across sigmas.

  Two traps, both of which gave me a wrong answer first time:
    - one block of 64 weights is pure noise. You need ~50k+ to measure this.
    - the int4 baseline must include an exact zero level. Space 16 levels
      evenly with no zero and you beat a strawman, not real int4.


==============================================================================
  5.  Double quantization: quantizing the quantizers
==============================================================================

  Every block of 64 weights needs its own absmax, stored as fp32. That scale
  is overhead on top of the 4 bits per weight:

      32 bits / 64 weights = 0.500 bits per weight

  Double quantization stores those absmax values as int8, and adds one fp32
  scale per 256 of them:

      8/64  = 0.125000        the int8 absmax
    + 32/(64 x 256)           the scale for those
      = 0.126953 bits per weight

      saved = 0.500 - 0.127
            = 0.373 bits per weight

  On 7.25B parameters:

      7,248,000,000 x 0.373 bits / 8 = 0.34 GB saved

  So the true cost of a 4-bit weight is not 4 bits, it is
  4 + 0.127 = 4.127 bits.
  Small in percentage terms, and the difference between fitting and not when
  you are 100 MB short. I was 73 MB short on the LoRA arm and lost the run.


==============================================================================
  6.  Paged optimizers
==============================================================================

  Adam keeps two moments per TRAINABLE parameter. In fp32 that is 8 bytes each:

      41,943,040 x 8 bytes = 320 MB

  In 8-bit it is 2 bytes each:

      41,943,040 x 2 bytes = 80 MB

      saved = 320 - 80 = 240 MB

  "Paged" means those states live in unified memory and spill to host RAM
  under pressure instead of raising out-of-memory. The saving is real: my LoRA
  run died asking for 168 MB with 95 MB free, a 73 MB shortfall, and 240 MB is
  exactly what this switch returns.


==============================================================================
  7.  LoRA, the textbook square case
==============================================================================

  Fine-tuning learns an update dW and adds it to the frozen weight W:

      W' = W + dW

  dW has the same shape as W, so training it costs as much as the model. The
  LoRA claim is that dW has low intrinsic rank, and can be factored:

      dW  ~  A @ B      A is (d x r),  B is (r x d),  r << d

  Worked for a 512 x 512 matrix at rank 8:

  dW is (512 x 512)        -> 262,144 parameters
  A  is (512 x 8)        -> 4,096
  B  is (8 x 512)        -> 4,096
  ----------------------------------------------
  LoRA trains A + B       -> 8,192
  reduction               -> 32x   (3.125% of the full update)
  parameters not trained  -> 253,952

  The shape of the saving: you replace d x d with r x (d + d). Quadratic in d
  becomes linear in d. The bigger the matrix, the better the trade.

==============================================================================
  11.  Choosing r
==============================================================================

  r buys capacity and costs parameters, linearly. Same model, same targets:

      r       trainable   % of model   adapter (bf16)
  ---------------------------------------------------
      4      10,485,760      0.1447%            20 MB
      8      20,971,520      0.2893%            40 MB
     16      41,943,040      0.5787%            80 MB
     32      83,886,080      1.1574%           160 MB
     64     167,772,160      2.3147%           320 MB
    128     335,544,320      4.6295%           640 MB

  Doubling r doubles the trainable count exactly, because every term is
  r x (d_in + d_out). Rule of thumb for this size class: [8, 16, 32].
  I used r = 16: enough capacity for seven task formats, small enough that the
  adapter still ships as one 80 MB file.


==============================================================================
  12.  Why alpha exists
==============================================================================

  At inference the adapter is folded back in as

      W' = W + (alpha / r) x A @ B
             = W + (32 / 16) x A @ B
             = W + 2 x A @ B

  alpha/r is a fixed gain on the update. It exists so changing r does not
  silently change how strongly the adapter speaks: raise r for capacity and
  raise alpha with it to hold the scale. Merged this way the adapter costs
  ZERO extra latency, because W' is just a weight matrix again.

      7,248,000,000 x 2 bytes = 13.5 GB

  14.  Memory: full fine-tune vs LoRA vs QLoRA
==============================================================================

  Full fine-tune holds four things for EVERY parameter, plus an fp32 master
  copy because bf16 alone loses too much precision in the optimiser step:

      weights      7,248,000,000 x 2 bytes  =   14.5 GB
      gradients    7,248,000,000 x 2 bytes  =   14.5 GB
      optimiser    7,248,000,000 x 8 bytes  =   58.0 GB
      master fp32  7,248,000,000 x 4 bytes  =   29.0 GB
                                                ------
                                                 116.0 GB

  LoRA freezes the base, so gradients and optimiser state exist only for the
  41,943,040 trainable parameters:

      frozen base  =   14.5 GB
      adapter      =   0.08 GB
      grads        =   0.08 GB
      optimiser    =   0.34 GB
                     ------
                       15.0 GB

  QLoRA also stores the frozen base in 4-bit NF4:

      frozen base  =    3.6 GB
      quant consts =   0.12 GB
      adapter      =   0.08 GB
      grads + opt  =   0.42 GB
                     ------
                        4.2 GB      27x less than full

  CONFIRMED ON THE GPU. Resident memory after load, same card, same adapter:
      QLoRA (NF4 base)    4.9 GiB
      LoRA  (bf16 base)  13.7 GiB
  and at a 12,288-token window the bf16 arm ran out of memory on a 22 GB L4,
  twice, at step 6 of 156. It only fit at 8,192.
